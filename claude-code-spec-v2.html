三级降级决策树

每次任务开始前，先走这棵决策树确定执行模式。Agent Team 是首选，不满足条件才降级。

① Opus 4.6 可用 + Pro/Max 订阅？
YES → ② 已启用 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1？
YES → ③ 运行在 tmux / iTerm2 内？
YES → Tier 1：Agent Team + tmux 分屏 ✦ 首选
NO → Tier 2：Agent Team in-process（不分屏）
NO → Tier 2：先执行启用命令，再走 Tier 1/2
NO → Tier 3：Subagent 降级模式（功能受限）
首选
TIER 1
Agent Team + tmux
· Opus 4.6 / Pro or Max
· AGENT_TEAMS=1 已启用
· 在 tmux 或 iTerm2 内运行
· 可见各 agent 独立分屏
· 支持 agent 间实时通信
· 最高并行度，最强协作
降级 1
TIER 2
Agent Team in-process
· Opus 4.6 / Pro or Max
· AGENT_TEAMS=1 已启用
· 普通终端（VS Code / Ghostty）
· Shift+↑↓ 切换 agent 视图
· 协作能力保留，无分屏可见性
· 效果 ≈ Tier 1，观测性稍弱
降级 2
TIER 3
Subagent 降级
· 任意模型
· 无需实验特性启用
· agent 间无实时通信
· 委托模式：派发后等结果
· 不支持 agent 嵌套团队
· 适合简单、可独立分解任务

MCP 服务器

每个 MCP 在特定阶段发挥作用，Team Lead 负责调度调用，teammates 按需使用。

mempalace
跨会话持久记忆。存储架构决策(ADR)、踩坑记录、团队约定。

实时最新库文档，彻底杜绝幻觉 API 和过时用法。
P1 探索 · P3 实现中
Filesystem
结构化文件读写，带权限控制。所有文件操作必须经此 MCP。
P1 · P3 · P5
sequential-thinking
结构化推理链，复杂任务分解、风险分析、阻塞问题处理。
P2 规划 · P3 阻塞时
cc-recommender

Agent Team 结构

🎯
team-lead
orchestrator · delegate mode
唯一掌握全局上下文的角色。分解任务、分发给 teammates、汇总结果、与用户沟通、处理跨 agent 冲突。开启 Delegate Mode 后仅协调，不亲自写代码。
Read Task Message mempalace sequential-thinking cc-recommender
⚙️
impl-agent
implementer · git worktree
在独立 git worktree 中执行编码任务。每个原子变更提交一次 checkpoint。使用 context7 验证 API，使用 context-compress 管理自身 context。单次变更 ≤ 200 行。
Read Write Bash(git *) context7 Filesystem context-compress 无 DB 迁移权限
🧪
test-agent
tester · isolated context
监听 impl-agent 的变更，同步编写单元/集成测试，覆盖边缘情况，运行并汇报通过率。与 impl-agent 实时通信，当测试失败时通知对方修复。
Read Write(test/**) Bash(npm test) Bash(pytest) 禁止修改 src/**
🛡️
review-agent
reviewer · fresh context
全新上下文，不共享 impl-agent 的编码历史，消除偏见盲点。检查安全漏洞、逻辑缺陷、架构合规。输出带行号的结构化 Review 报告，阻断问题时通知 lead。
Read Grep Glob 只读，禁止写入

执行规范
六阶段详细规范

点击阶段卡片展开详情。

P0
记忆唤醒 Memory Init
任务开始前的热身。Lead 独自运行，约 1-2 分钟。
team-lead
Lead mempalace 检索历史决策：查询本项目的架构决策(ADR)、已知踩坑、团队约定。Lead 将摘要注入自身 context 和 AGENTS.md。
Lead cc-recommender 获取推荐策略：根据任务类型获取最优 Agent Team 配置（需要几个 teammate、各自角色和权限）。
Lead context7 预热文档：若任务涉及特定库，提前拉取最新 API 文档片段，注入到 teammates 启动时的 context。
✦ Tier 3 降级时：Lead 职责由主 Agent 承担，mempalace/cc-recommender 同样调用，流程不变。
P1
探索理解 Explore
Lead 派遣 impl-agent 做轻量探索，自身接收压缩摘要，不污染主 context。
team-lead impl-agent
Lead 派遣探索任务：向 impl-agent 发送探索指令：读取目录树、CLAUDE.md、入口文件、与任务相关的模块，输出压缩摘要。
impl Filesystem 定向读取文件：只读与任务直接相关的模块，不全量扫描。避免在 impl-agent 自身 context 里堆满无关文件内容。
impl context-compress 压缩探索结果：将读取内容提炼为结构化摘要（模块关系、关键接口、潜在影响点），发回给 Lead。
Lead 接收摘要：Lead 只消费压缩后的摘要，不直接读原始文件，保持主 context 干净。
✦ Tier 3：主 Agent 直接调用 Filesystem + context-compress，避免在主 context 里读大量文件。
P2
规划分解 Plan
输出书面计划，用户确认后才能进入 P3。这是最重要的质量门。
team-lead 用户确认
Lead sequential-thinking 结构化分解：按依赖顺序拆解为原子步骤，标注哪些可并行（交给不同 teammate）、哪些必须串行。
Lead sequential-thinking 风险识别：明确标出高风险操作（DB 迁移、Auth 修改、第三方 API 调用、删除操作），这些必须等用户二次确认。
Lead cc-recommender Team 配置确认：根据任务规模确认 teammate 角色和数量（小任务 2 人、标准 3-4 人、大任务考虑 worktree 隔离）。
用户 展示计划，等待批准：Lead 向用户展示完整计划（步骤 / 影响文件 / 风险点 / team 配置），收到 ✓ 后才进入 P3。严禁跳过此步。
⚠ 计划未经用户确认就开始执行是本规范最严重的违规行为。大于 3 个文件的变更，必须走 P2 门控。
P3
Agent Team 并行执行 Execute
三线并行：impl 写代码，test 同步跟测，review 持续审查。Lead 仅协调。
impl test review lead 协调
Lead 开启 Delegate Mode，派发任务给各 teammate，启动 Agent Team。此后 Lead 只协调，不写代码。
impl context7 API 验证优先：每次调用外部库前通过 context7 确认最新文档，不依赖训练数据中的 API 知识。
impl Filesystem 小步提交：每完成一个原子功能，通过 Filesystem 写文件 + git commit checkpoint。单次变更 ≤ 200 行。
test 实时跟测：监听 impl-agent 的变更通知，同步编写测试并运行。测试失败时通过 Team 消息系统通知 impl 修复。
impl context-compress Context 管理：impl-agent 自身 context 使用率 > 60% 时主动触发压缩，防止质量降级。
Lead sequential-thinking 阻塞处理：任何 teammate 遇到预期外问题时，上报给 Lead，Lead 用 sequential-thinking 分析影响后上报用户决策，不自行猜测解决。
✦ Tier 3：用 Subagent 分别委托编码/测试任务。Agent 间无实时通信，改为串行委托+汇总。impl 完成 → 委托 test → 委托 review。
P4
Review 闭环 Review
review-agent 全程独立，最终出具结构化报告。阻断问题必须修复后重跑。
review-agent lead 综合
review 全新 context 审查：review-agent 从未参与编码，无偏见地审查 diff。重点：注入/XSS/权限缺陷、凭证泄露、逻辑错误、架构违规。
review 输出结构化报告：分三级 — 🔴 阻断（必须修复才能 Ship）/ 🟡 警告（建议修复）/ 🟢 通过。附具体行号和修复建议。
test 测试覆盖汇报：test-agent 输出最终测试通过率，覆盖率报告，确认边缘情况已覆盖。
Lead 综合裁决：Lead 汇总 review 报告和测试结果。若存在 🔴 阻断，派发 impl-agent 修复并重新触发 review 循环，直到全绿。
⚠ Writer 和 Reviewer 必须是不同的 Agent，不共享编码上下文。同一 Agent 自我审查不算有效 Review，不得跳过。
P5
记忆固化 & 交付 Remember & Ship
本次任务的决策和经验写入 mempalace，为下一次 P0 积累养料。
team-lead 交付
Lead mempalace 固化架构决策：记录本次 ADR（选了什么方案、为什么、否决了什么）。下次同类任务 P0 时直接复用。
Lead mempalace 踩坑归档：记录执行过程中遇到的意外问题和解决方案（包括 Agent Team 协调中遇到的 teammate 失败、权限冲突等）。
Lead Filesystem 更新 CLAUDE.md + AGENTS.md：将新发现的项目规范追加到两个文件，确保下次所有 teammates 读取时得到最新约定。
交付 生成变更摘要：Lead 输出完整交付报告（修改文件列表 / 测试结果 / review 结论 / 风险说明），移交用户。
团队记忆文件
AGENTS.md 模板

Agent Team 专用的团队级记忆文件。所有 teammates 启动时都会读取。每一行都应由人工审批，不允许 AI 自动生成后不经审查就写入。

AGENTS.md · 项目根目录 
# ── AGENTS.md · Team 级执行约定 ─────────────────────
# ⚠ 此文件由人工审批维护，teammate 发现新约定需上报 Lead，Lead 请示用户后才能修改

## 团队角色约定
- team-lead    : 仅协调，开启 Delegate Mode，不直接写代码
- impl-agent   : 编码实现，git worktree 隔离，单次 ≤ 200 行
- test-agent   : 跟踪 impl 变更，同步写测试，实时汇报通过率
- review-agent : 全新 context，只读审查，出具三级 Review 报告

## MCP 调用约定
- mempalace         : 仅 Lead 在 P0/P5 调用
- context7          : impl-agent 使用外部库前必须调用
- context-compress  : 探索完成后 + context > 60% 时
- sequential-thinking: Lead 在 P2 规划和遇到阻塞时调用
- Filesystem        : 所有文件操作必须经此 MCP，禁止 shell 直读
- cc-recommender    : P0 策略 + P2 team 配置推荐

## 高风险操作（必须 Lead 请示用户确认后才能执行）
- 数据库 schema 迁移
- Auth 相关代码修改
- 生产环境配置变更
- 删除超过 10 个文件的操作
- 第三方 API 密钥更换

## 禁止事项
- ❌ 跳过 P2 用户确认直接进入 P3
- ❌ Writer 和 Reviewer 共享 context
- ❌ Teammate 嵌套生成子 Team（改用 Subagent 委托）
- ❌ context 超 85% 后继续执行（必须保存并开新会话）
- ❌ 硬编码密钥或凭证
- ❌ 使用未经 context7 验证的第三方 API

黄金规则
不可妥协的执行原则
🎯
Agent Team 优先，Subagent 降级
每次任务开始先走三级决策树。具备条件时必须用 Agent Team，不允许因为"省事"直接用 Subagent。
📋
计划先行，代码在后
P2 的书面计划必须用户确认。涉及 >3 个文件的变更强制走 P2 门控，不得绕过。
🔒
Writer ≠ Reviewer（上下文隔离）
review-agent 必须是全新 context，不能是写了代码后再自我 Review 的同一 Agent。
🧩
Teammate 不嵌套 Team
Teammate 内部的子任务只能用 Subagent 委托，不允许嵌套生成新 Team，否则 token 成本指数爆炸。
🛑
遇阻即停，上报 Lead
Teammate 遇到预期外问题时停止执行并上报，不允许自行猜测解决高风险操作。Lead 负责决策和用户沟通。
🧠
P5 记忆固化是强制步骤
任务结束不写 mempalace，下次 P0 就是空手起步。记忆固化和代码交付具有同等重要性。
